part 1: images

there two different types of optimization we can do, either memory usage optimization, or file size optimization. keep in mind that these are two different things that don't correlate too much to each other!

"but if the file is smaller, doesn't that mean less is loaded?"

well, yes, but actually no (ebk)

while file size cool and all, the goal of optimization is to make sure that whatever engine you are using can actually handle all of the things you want to do. if you want flashy high def sprites, that's cool, but everything comes at a cost, and you need to find a perfect middle ground of what looks cool and what is worth making everybody's computer run. i love shaders as much as the next guy, but if the next guy is someone with a really poor GPU then he actually freaking hates you.

when you "optimize" your images through something like oxipng to compress images, you're only compressing the file size of the image, not what is actually loaded into memory. the VRAM indicator you see on top of most fnf builds indicate how many MB worth of images it is having to hold in memory, and the more it holds the more strain is being put on the program to run.

  • MB: Megabytes (1,000,000 or 10^6 bytes)
  • Mb: Megabits (1,000,000 or 10^6 bits), [8x smaller than a MB!]
  • MiB: Mebibytes (1,048,576 or 2^20 bytes), calculated using base 2, because computers especially love factors of 2

for optimizing memory usage, you need to actually compress what the vram is holding, and the best way to do that is to tinker with the resolution of any images being loaded. this involves:

  • trimming out as much transparent space as you can
  • scaling down images as much as you can
  • using the least amount of images

if you've been wondering why adobe texture atlases are the new big priority in fnf modding, this is because it manages to hit all three bullet points at the same time! WOW!
